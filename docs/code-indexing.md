# Индексация кодовой базы (для крупных проектов)

Для маленьких репозиториев агенту хватает grep и чтения файлов. Индексация
нужна, когда проект большой: десятки тысяч файлов, и вопрос «где это
реализовано» стоит минут чтения. Здесь — опенсорсные варианты, встроенные
в kit **выключенными по умолчанию**: включаются только там, где реально надо.

## Что встроено: Serena (рекомендовано по умолчанию)

[Serena](https://github.com/oraios/serena) — MCP-инструментарий символ-уровня
через language-серверы (LSP): поиск символов, ссылки, иерархия, точечные
правки. 40+ языков. Ноль инфраструктуры: не строит индекс, не тратит токены
на эмбеддинги, работает на лету. Лицензия: MIT (LSP-ядро) / GPL-3 (приложение).

В `opencode/opencode.jsonc` он уже прописан **с `enabled: false`**:

```jsonc
"serena": {
  "type": "local",
  "command": ["uvx", "--from", "git+https://github.com/oraios/serena",
              "serena", "start-mcp-server", "--context", "ide-assistant"],
  "enabled": false
}
```

Включить: поставь `"enabled": true` и `docker compose up -d`. Первый запуск
скачает language-серверы нужных языков (кэшируются). Контекст `ide-assistant`
отключает дублирующие файловые утилиты — в kit'е они уже есть у агента.

Альтернатива без правки глобального конфига: положи `opencode.json` с этим
блоком (`"enabled": true`) в корень конкретного проекта — Serena включится
только там.

## Вариант: open-codebase-index (семантический поиск)

[open-codebase-index](https://github.com/Helweg/open-codebase-index) — гибрид
эмбеддингов + BM25, **нативный плагин OpenCode**, локальный SQLite-индекс,
инкрементальная переиндексация с учётом веток.

В образе kit'а пакет уже установлен (запинен `ARG CODE_INDEX_VERSION`) и
**спит**: он не подключён глобально и не вызывается никогда, пока ты явно
не включишь его для конкретного большого проекта. `autoIndex` выключен —
эмбеддер срабатывает только на явной команде `/index`.

### Включение для одного проекта (три файла)

**1. `.env` — тот же эмбеддер, что у памяти (OpenRouter):**

```env
OPENROUTER_API_KEY=sk-or-...
```

**2. В корне большого проекта — `.opencode/codebase-index.json`:**

```json
{
  "embeddingProvider": "custom",
  "customProvider": {
    "baseUrl": "https://openrouter.ai/api/v1",
    "model": "qwen/qwen3-embedding-8b",
    "dimensions": 4096,
    "apiKey": "{env:OPENROUTER_API_KEY}",
    "maxTokens": 8192
  },
  "indexing": { "autoIndex": false, "requireProjectMarker": true }
}
```

`{env:OPENROUTER_API_KEY}` — ключ подставляется из окружения и никогда не
попадает в файл проекта. `dimensions` = 4096 у `qwen3-embedding-8b`; если
провайдер вернёт иное, `index_status` сообщит об этом явно.

**3. Там же — `opencode.json` с плагинами** (перечисляй оба: конфиг проекта
может перекрыть глобальный список, а экстрактор памяти нужен всегда):

```json
{
  "plugins": [
    "/opt/graphiti-extractor",
    "/usr/local/lib/node_modules/open-codebase-index"
  ]
}
```

**4. В боте: `/index`** — первый индекс создаст эмбеддинги (дальше —
инкрементально, только изменённое). Индекс лежит в `.opencode/index/`
проекта и попадает в `.gitignore`.

Смена эмбеддера или модели — только с принудительной пересборкой
(`index_codebase` с `force: true`), иначе старые векторы деградируют поиск.

Когда выбирать вместо Serena: вопросы формулируются смыслом («где мы
публикуем события заказа?»), а не именами символов; проект полиглотный;
нужен поиск по истории вызовов. Плата: время на первичную индексацию,
место под индекс, расходы на эмбеддинги (если не Ollama).

## Эмбеддер индекса и эмбеддер памяти — независимы

Совпадать с эмбеддером памяти (Graphiti) **не нужно и не полезно**: это два
раздельных векторных пространства, между собой они никогда не сравниваются.
Более того, для кода часто лучше взять отдельную модель (`nomic-embed-code`,
`jina-code` или бесплатный локальный Ollama) — код-специфичные эмбеддинги
точнее текстовых, а на тысячах кусков кода дорогая модель жжёт деньги.

Единственное железное правило (для обеих систем): **эмбеддер на записи =
эмбеддер на поиске**. Сменил провайдера — переиндексируй проект, иначе
старые векторы деградируют поиск без всяких ошибок.

## Продвинутый вариант: codesearch (multi-repo)

[codesearch](https://github.com/flupkede/codesearch) — Rust-бинарник, гибрид
vector+BM25, полностью офлайн, режим `serve` для поиска сразу по нескольким
репозиториям (кросс-репо ранжирование). Нужен, когда работаешь с группой
сервисов одновременно. Для одиночного проекта избыточен.

## Важно: это пара, а не «или-или»

Векторная индексация не «второй сорт» — она решает задачу, которую LSP не
решает: **разрыв словарей**. Запрос «где мы валидируем номер телефона?» не
найдётся grep'ом, если в коде `normalizeMsisdn()`, и не найдётся Serena —
ей нужен символ-якорь, а его не знают. Гибридный поиск (вектор + BM25,
как в open-codebase-index и codesearch) сравнивает смысл, а не строки.

Справедливости ради: современные инструменты — гибриды (вектор + BM25 +
бустинг символов), а локальные эмбеддеры (fastembed, Ollama, ONNX) делают
их бесплатными и офлайн. Дорогой API-эмбеддер — выбор конфига, а не
неизбежность.

Рабочая пара на крупном проекте: **гибридный индекс — для обнаружения,
Serena — для точной навигации и правок**. Serena отвечает «где определение
и кто ссылается», вектор — «что вообще искать, когда слов в коде нет».

## Сводка

| | Serena | open-codebase-index | codesearch |
|---|---|---|---|
| Тип | LSP, символы | эмбеддинги + BM25 | эмбеддинги + BM25, multi-repo |
| Инфраструктура | ноль | SQLite-индекс | локальные векторы |
| Расходы | ноль | эмбеддинги (или Ollama) | ноль (fastembed локально) |
| Включение | флаг в конфиге | npm + индексация | бинарник + индексация |
| Когда | большие проекты, точные символы | смысловой поиск | много репо сразу |

## Правило

Маленький проект → ничего не включай. Большой проект → включай Serena;
если символьного поиска мало — добавляй open-codebase-index. После работы
над проектом можно выключить обратно.
